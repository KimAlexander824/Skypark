# Контракт сервиса распознавания (версия 1)

Как другие сервисы (backend) пользуются распознаванием лиц. Пока контракт не меняется,
каждый сервис можно переписывать как угодно внутри.

**Правило изменений:** добавлять новые поля и задачи можно свободно. Менять или удалять
существующие — только договорившись и подняв версию контракта.

## Как вызывать

Через очередь BullMQ в Redis.

| | |
|---|---|
| Redis | `REDIS_URL`: разработка — `redis://redis:6379`, продакшен — с паролем `redis://:${REDIS_PASSWORD}@redis:6379` |
| Очередь | `recognition` |
| Готовый клиент на Python | `services/recognition/client/recognition_client.py` — скопировать к себе, `pip install bullmq` |

```python
from recognition_client import RecognitionClient, RecognitionJobFailed

rc = RecognitionClient("redis://redis:6379")   # один на всё приложение

try:
    result = await rc.identify(photo_bytes, actor="staff:17", branch="chilanzar")
except (RecognitionJobFailed, TimeoutError):
    ...  # распознавание недоступно — искать ребёнка по телефону
```

Метод сам кладёт задачу в очередь и ждёт ответ (поиск — около 0,3 с, ждёт до 15 с).
Фронтенд делает к backend один обычный запрос и получает готовый ответ.

**Кто сделал запрос.** Каждое действие с биометрией пишется в журнал доступа. Сервис не знает
пользователей, поэтому backend передаёт в задаче `actor` (кто, например `"staff:17"`) и `branch`
(филиал). В клиенте: `await rc.identify(photo, actor="staff:17", branch="chilanzar")`.
Поля необязательные, но в продакшене передавайте их всегда — иначе по журналу не понять, кто искал ребёнка.

Клиент сам ставит повторы при сбоях (3 попытки, экспоненциальная пауза от 1 с) и приоритеты:
поиск — самый срочный, регистрация — следом, фоновые задачи — последними.

## Задачи

Фото передаётся в поле `photo` как base64: только JPEG или PNG, до 10 МБ и до 50 млн пикселей.
`child_id` — целое число от 1 до 2 147 483 647.

После обработки фото **удаляется из задачи** в Redis (при сбое — после последней попытки):
в данных выполненной задачи поля `photo` уже нет, результат остаётся.

### `identify` — найти ребёнка по фото

Данные: `{"photo": "<base64>"}`

Результат:
```json
{
  "ok": true,
  "status": "found",
  "child_id": 7,
  "confidence": 0.93,
  "message": "Ребёнок найден",
  "candidates": [{"child_id": 7, "confidence": 0.93, "is_match": true}]
}
```

| `status` | Что значит | Что делать |
|---|---|---|
| `found` | ребёнок найден | открыть карточку `child_id` |
| `not_found` | похожих нет | регистрация или поиск по телефону |
| `ambiguous` | 2+ детей почти одинаково похожи | сотрудник выбирает из `candidates` |

`candidates` — до 3 самых похожих детей. `confidence` — сходство от 0 до 1.

### `enroll` — запомнить лицо ребёнка

Данные: `{"child_id": 7, "photo": "<base64>", "source": "registration"}`

- `source = "registration"` — фото при регистрации, в кадре должно быть ровно одно лицо;
- `source = "visit"` — фото с повторного визита, берётся самое крупное лицо. Добавлять его стоит
  только при уверенном совпадении (`found` и `confidence` ≥ 0.6).

Результат:
```json
{"ok": true, "face_id": 15, "child_id": 7, "shard": 1, "det_score": 0.87, "source": "registration",
 "faces_count": 1, "ignored_faces": 0, "thumbnail": "<base64 JPEG>"}
```

- `thumbnail` — вырезка лица, которое запомнено. Фронтенд показывает её сотруднику: «Зарегистрировано
  это лицо — верно?». Если нет — `delete_faces` и переснять.
- `ignored_faces` — сколько мелких лиц на заднем плане не учитывалось. Если больше 0, в ответе есть
  `warning` с текстом для сотрудника — сверка по вырезке особенно важна.

Лица на заднем плане меньше 25% площади главного лица игнорируются (`MULTIPLE_FACES_MIN_RATIO`).
Если рядом стоит ещё человек сопоставимого размера — ошибка `multiple_faces`.

На ребёнка хранится до 5 фото: фото с регистрации — всегда, остальные места занимают самые свежие.

### `delete_faces` — удалить биометрию ребёнка

Данные: `{"child_id": 7}`. Backend кладёт эту задачу, когда удаляет ребёнка или родитель
просит удалить фото (§42). Повторный вызов безопасен.

Результат: `{"ok": true, "child_id": 7, "deleted": 3}`

### `sync_children` — сверка: удалить лица детей, которых нет у backend

Данные: `{"child_ids": [1, 2, 7, ...], "dry_run": false}` — **полный** список существующих детей.

Нужна, если `delete_faces` потерялась (Redis перезапустился, backend упал между удалением ребёнка
и отправкой задачи). Backend запускает её раз в сутки, ночью. Всё, чего нет в списке, удаляется.

Результат:
```json
{"ok": true, "dry_run": false, "known": 1520, "stored": 1498, "orphans": [313], "deleted": 2}
```

- `dry_run: true` — только показать, кого удалила бы (`orphans`), ничего не удаляя.
- Защита от ошибки backend: пустой список — отказ (если база детей правда пуста — `"allow_empty": true`);
  удалить больше 20% детей (и больше 5) — отказ (если это верно — `"force": true`).
  Отказ — ответ `{"ok": false, "error": "sync_refused", "message": ...}`.

В клиенте: `await rc.sync_children(all_child_ids)`.

## Ошибки

**Плохое фото — это обычный ответ, а не сбой.** Задача завершается (`completed`) с результатом:

```json
{"ok": false, "error": "no_face", "message": "Лицо не найдено. Сфотографируйте ребёнка анфас при хорошем свете"}
```

| `error` | Когда | Что показать сотруднику |
|---|---|---|
| `bad_image` | файл не читается как картинка или не JPEG/PNG | выбрать другой файл |
| `photo_too_large` | больше 10 МБ или больше 50 млн пикселей | уменьшить фото / снять заново |
| `no_face` | лицо не найдено | переснять анфас при хорошем свете |
| `low_quality` | лицо меньше 80 px | подойти ближе |
| `multiple_faces` | при регистрации рядом с ребёнком ещё одно крупное лицо (≥ 25% площади) | переснять одного ребёнка |

`message` можно показывать сотруднику как есть.

**Сбой** (база или нейросеть недоступны) — задача повторяется автоматически. Если все попытки
не удались, задача получает статус `failed`. Клиент в этом случае бросает `RecognitionJobFailed`:
сотрудник ищет ребёнка по телефону (§43).

**Неверная задача** (нет поля, `child_id` не число, неизвестное имя) — сразу `failed`, без повторов.

## Регистрация ребёнка без общей транзакции

У сервисов разные базы, поэтому «сохранить ребёнка и лицо одной транзакцией» нельзя.
Порядок действий:

1. `identify` — проверить, нет ли ребёнка уже в базе (`found` → показать «похоже, уже зарегистрирован»).
2. Создать ребёнка у себя, получить `child_id`.
3. `enroll` с `source="registration"`.
4. Если `ok: false` (плохое фото) или `RecognitionJobFailed` — удалить ребёнка у себя
   (или пометить «без фото») и попросить переснять.

## Удаление ребёнка

Внешнего ключа между сервисами нет. Удаляя ребёнка, backend кладёт задачу `delete_faces`.

## Хранение задач

Фото удаляется из задачи сразу после обработки. Сами задачи (данные без фото и результат)
удаляются из Redis через 10 минут после выполнения, упавшие — через час. За это время backend
должен забрать результат. В продакшене Redis не пишет данные на диск.

Если в результате `enroll` есть `thumbnail` (вырезка лица) — это биометрия: backend не хранит её
дольше, чем нужно для показа сотруднику.
